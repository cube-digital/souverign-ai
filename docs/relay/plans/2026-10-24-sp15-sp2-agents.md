# SP1.5 + SP2 — Hardening, Tester Access, Agents in Chat, Ops Bots Plan

**Goal:** testers reach the app over Tailscale safely; every user creates agents (General, DevOps, QA templates), invites them into chats, and they answer on the local LLM through Hermes, with the DevOps/QA bots reading a simulated ops backend: Janosch's three use cases, live in the app.
**Spec:** docs/superpowers/specs/2026-10-24-sovereign-agents-demo-design.md (§4 A2, A7, §5.2 F1, §8.2, §8.3, §9, §11 SP1.5 + SP2, amendments 8, 12, 13) + decisions.md (D-8, D-9). Mockups: docs/design/mockups/ (`Main.dc.html` agent replies, `Agent.dc.html`, `Presenter.dc.html`). Code map: SP1 as merged on main @ 26cd336.
**Architecture:** the relay now requires a short-lived **ticket** signed by the bridge (HMAC with `RELAY_ADMIN_TOKEN`) at hello. Each **agent** is a device hosted by the bridge: its keys sit encrypted in Postgres, it runs a `ChatEngine` from `@sa/client` like a browser does, and it answers through its own **Hermes profile** (local vllm-mlx, built-in toolsets off). Hermes reaches back through the **bridge MCP server**, which exposes per-template tools: `chat_read` for all, plus ops tools proxied to **`services/ops-sim`**, a simulated ops backend with nodes, raft, DB sync, user presence, QA runs and tickets.

## Decisions (demo-first)

- **Tickets:** `payload.sig`, payload = base64url JSON `{d: device_id, e: expires_ms}`, sig = HMAC-SHA256(`RELAY_ADMIN_TOKEN`, payload). TTL 12 h. The bridge mints them for the caller's own devices and for its agent devices; the relay verifies at hello and on `/relay/debug/recent`. No new secret to distribute.
- **Key envelopes are trusted only from the chat owner's devices.** Only the owner changes membership (SP1), so only they create epochs.
- **Agent secrets:** agent device secret keys are encrypted with AES-256-GCM under `sha256(BRIDGE_MASTER_KEY)`. The Hermes API key and the agent's MCP token are derived, not stored: `hmac(BRIDGE_MASTER_KEY, "hermes:" + agentId)` and `agentId + "." + hmac(BRIDGE_MASTER_KEY, "mcp:" + agentId)`.
- **An agent answers only when addressed** with `@<name>` (case-insensitive), at most one reply per 3 s per chat, one turn at a time per agent. Context = the chat's last 20 messages the agent was allowed to see (it never received earlier ones: new epoch + relay window).
- **Replies carry what the agent used:** the text body gets an optional `meta: {tools?, ms?}`, which the UI shows as "Used cluster_health, metric_trend · 18.4 s" (mockup).
- **Templates** live in `infra/hermes/templates/{general,devops,qa}.md` (SOUL text) and in a fixed tool allowlist per template in the bridge. The user's own `soul` text is appended under "Personality and rules".
- **The simulated backend is a stand-in for the customer's systems** (we have no access to the client's real systems): the same MCP "connector" pattern later points at real Confluence, GitLab, Jira or monitoring (next plan).
- **Tests use `AGENT_RUNTIME=echo`** (a fake runtime that lists what is in its context) so e2e is fast and deterministic. A separate live smoke runs the real DevOps bot on the local LLM.
- **Tester access:** `make demo` runs the built web app with `vite preview` (same proxy as dev, `.ts.net` hosts allowed) and keeps the Mac awake; `make share` publishes it with `tailscale serve` over HTTPS. Installing Tailscale and inviting testers are human steps.
- **Presenter view:** `/presenter` shows four iframes `/?slot=1..4`; the session key is per slot (`sa.session.<slot>`), so each frame signs in as a different user.

## Review Focus

- Every relay path that serves data checks a valid, unexpired ticket for the same device; the bridge mints tickets only for devices the caller owns.
- An agent never sees messages from before its invite, never answers unaddressed, and its tools are limited to its template's allowlist (an MCP call for another template's tool fails).
- Agent processes: no orphaned Hermes gateways after bridge shutdown; port allocation stays within 8701–8709; a failed start sets status `error` and the chat gets a clear message rather than silence.
- Agent secret keys never leave the bridge unencrypted at rest; derived tokens are compared in constant time.

`packages/protocol/src/ticket.ts` (Node only, complete):

```ts
import { createHmac, timingSafeEqual } from "node:crypto";

export function signTicket(
  secret: string,
  deviceId: string,
  ttlMs: number,
  now = Date.now(),
): { ticket: string; expires_at: number } {
  const expires_at = now + ttlMs;
  const payload = Buffer.from(JSON.stringify({ d: deviceId, e: expires_at })).toString("base64url");
  const sig = createHmac("sha256", secret).update(payload).digest("base64url");
  return { ticket: `${payload}.${sig}`, expires_at };
}

export function verifyTicket(secret: string, ticket: string, deviceId: string, now = Date.now()): boolean {
  const [payload, sig] = ticket.split(".");
  if (!payload || !sig) return false;
  const expected = createHmac("sha256", secret).update(payload).digest();
  const given = Buffer.from(sig, "base64url");
  if (given.length !== expected.length || !timingSafeEqual(given, expected)) return false;
  try {
    const { d, e } = JSON.parse(Buffer.from(payload, "base64url").toString("utf8"));
    return d === deviceId && typeof e === "number" && e > now;
  } catch {
    return false;
  }
}
```

### T4: Bridge: tickets, rate limit, agents data and routes

### T5: Client hardening

- `RelayClient` options gain `getTicket: () => Promise<string>`, called before every hello (first connect and each reconnect); `hello` sends `{device_id, ticket}`. A `bad_ticket` error triggers one immediate retry with a fresh ticket, then backoff.
- `ChatEngine` options gain `isTrustedKeySender?: (chatId: string, senderDevice: string) => Promise<boolean>` (default: trust all). `incomingKey` ignores keys whose sender is not trusted (logs `key_untrusted` with ids), checked before `putChatKey`.

Tests (`packages/client/test/engine.test.ts`, `FakeRelay`): a key sealed for this device by a non-owner device is ignored and later messages in that epoch stay `pending`; the owner's key is accepted. (Ticket refresh is covered by e2e.)

- `src/mcp/server.ts`: MCP over streamable HTTP at `POST/GET/DELETE /mcp`, stateless (a new server and transport per request, `sessionIdGenerator: undefined`), using the installed `@modelcontextprotocol/sdk` (check its README for the current server class names; v2 may rename them). `Authorization: Bearer <mcp token>` → `verifyMcpToken` → agent, else 401. Tools registered by template:

  The ops tools proxy to `OPS_SIM_URL` (default `http://127.0.0.1:8649`) and return its JSON as text. Each call is recorded in a per-agent `ToolLog` (`begin(agentId)`, `record(agentId, {name, args, result, ms})`, `end(agentId) → TraceStep[]`), with args truncated to 500 chars and the result to 1500, so T8 can attach the steps to the reply.
- Reasoning: `AgentRuntime.chat` returns `{ content: string; reasoning?: string }`. `HermesRuntime` fills `reasoning` from whatever the pinned Hermes exposes. Check, in this order: a `reasoning_content` or `reasoning` field on the chat-completion message; the Responses API `reasoning` output items; the Runs API events (`/v1/runs/{id}/events`). Use the first that works and document which one in a comment. If none does, leave it empty: the UI then shows tool steps only. Strip any `<think>…</think>` from `content` and move it into `reasoning`. `EchoRuntime` returns `reasoning: "echo: looked at N messages"`.

### T8: Agent host in the bridge

`src/agents/host.ts`: `class AgentHost`, created in `main.ts` with `{ db, runtime, relayInternalUrl, adminToken }` and passed to `buildApp`.
- **Start:** for each agent with chats, build a device: decrypt keys, open a `PgKeyStore` (implements `KeyStore` over `sa.agent_chat_keys` with encrypted keys and `sa.agent_cursors`), then a `RelayClient` (url `ws://` + relay host + `/relay/ws`, tickets minted locally with `signTicket`), then a `ChatEngine` with `isTrustedKeySender` (owner devices from the DB). Then `start(chatIds)`. `onAgentAdded` starts the device or adds the chat and syncs it; `onAgentRemoved` stops tracking the chat.
- **Every `ok` message** is stored in `sa.messages_plain` (its own included).
- **Gates for a reply:** the body is text, the sender is not this agent, the text contains `@<agent name>` (case-insensitive, word boundary), the agent is an active member, and its last reply in this chat was 3 s ago or more. Turns are serialized per agent.
- **Turn:**
  1. `runtime.ensureStarted(agent)`.
  2. The system message is `You are <name> in the chat "<title>" (chat_id <id>). Messages you can see, oldest first:` followed by the last 20 stored messages as `Name: text`.
  3. The user message is the addressing text.
  4. `toolLog.begin`, then `runtime.chat`, then `toolLog.end`.
  5. `engine.sendText(chatId, reply.content)` with body `meta: {tools, ms, trace}`, where `trace` is the thinking step (if `reasoning` is non-empty, truncated to 4000 chars) followed by the tool steps in call order. Extend `sendText` to accept an optional meta only if T5 did not; otherwise send the body through the engine's existing body path.
- **On a runtime error:** send `"I can't answer right now (the local model is not available)."` with `meta: {tools: [], ms}` and set the agent status to `error`.
- `stopAll()` on shutdown closes the engines.

Tests (`services/bridge/test/host.test.ts`, PGlite + a fake relay link + `EchoRuntime`): an unaddressed message gets no reply; an addressed one gets a reply whose body carries `meta.tools`, `meta.ms` and a `meta.trace` that starts with the echo thinking step; messages from before the agent's membership never reach its context (the echo reply lacks a pre-invite sentinel and contains a post-invite one).
